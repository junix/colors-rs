01 · chromap 把颜色运算收敛到一个规范表示上

chromap 是一个 Rust 颜色工具库，外加一个叫 chromap 的命令行。它回答三件日常问题：这个颜色换成别的写法是什么；一组颜色怎么排得看起来顺；前景压在背景上够不够清楚。

库内部只认一种存储：带 alpha 的伽马编码 sRGBA，分量都在 0 到 1 之间。要感知运算时先换到 OKLab/OKLCH，算完再换回来——每一次换算都从规范表示出发、回到规范表示，中间不留第二种真值。超出 sRGB 色域的颜色用二分法只降饱和度（chroma），明度和色相尽量不动。

命令行把这套能力暴露成十一个子命令，输出走三条路：给人看的终端色块、可以直接进管道的 --json、以及带棋盘格衬底的 PNG 色卡。它通过 npm 分发：包里带全部 Rust 源码，第一次运行时在本机编译进用户缓存，之后直接复用。

它不追求成为色彩管理的全部：没有 ICC 配置文件，CMYK 只是数学近似，色差也不是 CIEDE2000。边界在取舍一节里逐条说清。

01 · 为什么只存伽马 sRGBA这是 CSS、终端与位图共同的语言，进出都不需要转换设备。代价是每次进感知空间都要重算一次矩阵与立方根——一次运算微不足道，但意味着库里不存在"以 OKLCH 为真值"的路径。分层那一节画的就是这一点。

02 · 八件它替你做的事

  • 一种规范存储：颜色统一存成伽马 sRGBA 加 alpha，所有运算共用同一份表示；适合不希望在两套表示之间出现漂移的代码。
  • CSS 子集解析：hex（3/4/6/8 位）、rgb()/hsl()、CSS 具名色与 transparent；适合直接吃前端与设计稿里的字符串。
  • 七种空间互转：linear sRGB、HSL、HSV、CMYK、OKLab、OKLCH 双向往返；适合把"换个写法"和"换个空间"分开处理。
  • 感知混色与渐变：默认在 OKLab 上插值，色相可选走短弧或长弧；适合做不发灰的过渡。
  • 调色板生成：明度标尺、黄金角、互补/三角/四角和声、tints/shades/tones；适合一次拿到一套成体系的颜色。
  • 色域映射：超出 sRGB 时二分收敛只降 chroma，保住明度与色相；适合把设计稿里的 Display-P3 值安全落地2。
  • WCAG 对比度：测比值、从候选里挑、自动沿明度修到 AA/AAA；适合在生成配色的同时保证可读。
  • 三种交付：ANSI 色块、≤256 色的 PNG 色卡、--json 结构化输出；适合终端预览、文档插图和脚本消费。

这八条到此为止：每条能力内部怎么算属于下一层文档。它们共享同一条主线，也就是主走查那一条。

这八条能力里，前六条属于库、后两条属于命令行。库不认识终端也不认识 PNG；命令行不自己算颜色，只决定把哪一段结果交给谁渲染。这个分工就是下面两张图的分界。

02 · 色域映射只发生在一条边上库里 OKLCH 到 sRGB 有两扇门：一扇只收已在色域内的值（越界就报错），另一扇自动收敛。命令行走的是第二扇，因此用户永远不会因为"颜色太鲜艳"而拿到错误。

03 · 一条调用链，三个出口

整个仓库交付两段程序：npm 启动器负责把调用方的要求转交出去，chromap CLI 负责解析与渲染，真正的颜色运算全部在核心库里。CLI 是唯一决定输出形态的地方——它把 ANSI 色块写进终端、把 PNG 色卡写进文件系统、把 JSON 留给标准输出。

八个盒子各自负责一件事。用户敲的是 chromap，脚本 spawn 的也是它，但两者真正落到的是 npm 启动器；启动器不认识颜色，它只保证有一个可用的可执行文件，缺了就让 Cargo 现场编译一次。chromap CLI 是焦点节点：它解析参数、调用核心库、然后决定结果去哪——终端拿 ANSI 色块、文件系统拿 PNG、标准输出拿纯文本或 JSON。核心库对这三条出路一无所知。

走一遍取色路径：用户敲 chromap convert "#3b82f6" → npm 启动器找到可执行文件并把参数原样透传 → chromap CLI 调核心库完成换算 → 把 hex 写进标准输出。换 --png out.png 时，前三步不变，最后一步改道去文件系统。

一个容易混的边界：终端与文件系统画在包边界之外，因为换一个输出目标（比如写成 stdout 的二进制 PNG）不影响包内的三个盒子；Cargo 构建缓存也在边界之外，它属于用户机器，而不是这个包。按预算删掉的是终端的 256 色降级细节与 Cargo 工具链本身——前者是 CLI 内部的一次分支，后者是所有人的公共依赖。

04 · 主走查：从色值到色卡

下面这条链贯穿全系统，后面三张图都是它的某一段放大。六个环节各点名它经过的组件与它做的一件事。

  1. 入参解析——chromap CLI 拆出子命令、目标色、数量与输出开关，并在入口一次性判定要不要 ANSI、要不要 JSON。
  2. 色值规范化——核心库的解析器把 CSS 子集字符串变成规范 sRGBA；不认识的写法在这里就报错，不往后传。
  3. 调色板生成——在 OKLCH 上按和声、黄金角或明度标尺铺开，得到一组仍可能超出 sRGB 的候选色。
  4. 色域映射——超出 sRGB 的候选逐个做二分收敛，只降 chroma，明度与色相尽量保住。
  5. 对比度校验——按 WCAG 公式算前景对背景的比值，不达标就沿明度二分修复，并在变亮与变暗之间取感知距离更小的那个。
  6. 渲染交付——同一份结果走三条出口之一：ANSI 色块、PNG 色卡、JSON 文本。

05 · 核心库分层：所有道路都经过规范存储

把核心库按"谁依赖谁"拉开，是一张以规范存储为中心的图：解析层只往里写，输出格式只从里读，空间转换与它双向往来，感知运算则同时依赖这两者。没有任何一条路能绕开规范存储直达另一个空间。

五个盒子各自负责一件事。解析层只认识字符串，它把合法输入送进规范存储，非法输入就地变成错误；空间转换是唯一懂"另一个空间"的模块，和规范存储之间是双向的两条边；感知运算（混色、调色板、对比度、距离）需要感知几何，所以它依赖空间转换，再由空间转换替它回规范存储；输出格式化是纯函数，只读不写。

走一遍调色板路径：感知运算要生成调色板 → 先经空间转换把基准色转到 OKLCH → 在 OKLCH 上铺开候选 → 每个候选经空间转换回到 sRGB（超界的在这里收敛）→ 落回规范存储交给输出格式化。中间任何一步都不直接持有第二种表示。

一个容易混的边界：「感知运算 → 空间转换」这条边说的是依赖，不是数据流——运算层调用的是换算函数，而不是把颜色存过去。按预算删掉的是错误类型与可选的 serde 特性，它们不改变这张依赖方向。

06 · 调色板的数据流：一条主线，三个出口

拿主走查里最长的一段——chromap palette --png out.png——按"这一步归谁负责"分成三条泳道。入口只做一次解析，颜色核心负责全部运算，输出渲染把同一份结果翻译成三种形态。粒子沿主线跑，能看到数据在哪里分岔。

三条泳道就是三个负责方。入口只解析参数、判定输出开关，不碰颜色；中间一条是颜色核心，四个节点串成主线——字符串进来，一份已在 sRGB 色域内的色板出去；最下一条是输出渲染，三个节点各自只做翻译，不再改值。

走一遍粒子主线：参数解析把色值字符串交给色值解析 → 得到规范 Color → 调色板生成在 OKLCH 上铺开 → 色域映射逐个收敛 → 对比度校验放行或修复 → 同一份色板同时可供终端色块、PNG 与 JSON 三个出口。三个出口的粒子跑的是同一个周期，只是相位不同。

易混点：色域映射在对比度校验之前，顺序不能换——先修对比度再映射色域，可能把刚修好的比值又破坏掉。JSON 节点画成外部样式，是因为它面向的是机器消费方而不是人眼。按预算删掉的是 CSS 变量前缀输出与 --dry-run 分支，它们都是渲染层的变体，不改变主线。

07 · 首次运行时序：npm 包为什么能覆盖三个平台

npm 上发布的不是二进制，而是完整 Rust 源码。启动器在每次被调用时，按"版本 + 平台 + 架构"在用户缓存目录里找可执行文件：找不到就让 Cargo 编译一次，找得到就直接复用。这是首次运行慢、之后零开销的来源。

五条生命线，一条主动。调用方只发一条消息就等结果；npm 启动器从第一步活到最后一步，它的激活条贯穿全图；Cargo 构建缓存只在 ALT 框里被访问，两个分支必落其一；chromap CLI 直到第六步才登场，它对前面发生过什么一无所知；stdout/stderr 只收最后一条消息。

易混点：ALT 框里的两条分支是二选一，不是先后执行；③ 与 ⑤ 的箭头方向相同，区别在写缓存还是读缓存。④ 是返回消息，用更细的线画。第七步说的"分流"是同一进程里的两个通道——结果进 stdout、诊断进 stderr，这样 --json 的输出可以直接进管道。按预算删掉的是 Cargo 工具链缺失时的报错分支与版本升级后的缓存失效重建。

08 · 五个已经做出的取舍

取舍换来什么代价
只存规范化的伽马 sRGBA库内只有一种真值，换算方向永远可逆每次感知运算都要重算一次空间矩阵
感知运算放在 OKLab/OKLCH 上混色不发灰、明度标尺符合直觉色差不是 CIEDE2000，数值不能当行业标准用
CMYK 不带配置文件零依赖、零配置，纯数学可复现只能当近似，不能直接付印
npm 发源码而不是预编译产物一个包覆盖三平台，无需发布矩阵首次运行要等一次本地编译
stdout 只放结果，诊断走 stderr--json 可直接进管道与 jqPNG 写盘提示在 stderr，人眼有时会错过
展开：透明色为什么测不了对比度

WCAG 的比值公式只对不透明颜色有定义。带 alpha 的前景必须先压在一块画布上合成出不透明结果，才能参与比较；所以库里带 alpha 的对比度入口要求显式给出一块底色，而不是悄悄假设白色。终端色块对透明色也是同一招：分别压在深、浅两块底色上各画一格。

展开：色域映射为什么用二分而不是公式

收敛只动 chroma、不动明度与色相，在这个约束下"色域内最大 chroma"是一个单调的边界，二分 32 次就能稳定逼近。它比解析式映射更容易保住"越界越少、改动越小"的性质，代价是每次映射要做数十次空间换算。
